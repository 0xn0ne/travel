# 旅行规划系统 — 需求文档

## Problem Frame

**核心痛点**：年轻人旅行规划面临两个断层——(1) 从"模糊想法"到"可执行行程"之间缺乏桥梁，用户说"我想去杭州玩两天"却不知道从哪开始；(2) 现有AI行程工具输出千篇一律的景点排列（"西湖→灵隐寺→河坊街"），缺乏"一个很会玩的本地朋友"那种有个性的推荐。

**差异化定位**：不做"又一个AI行程生成器"，而是做一个**品味行程生成器**——用人工策展的品味数据 + LLM 的叙事能力，生成有温度、有节奏、有惊喜的个性化行程。核心价值不是"帮你搜索景点"（高德/携程已经做了），而是"帮你发现你会喜欢但自己找不到的地方，并且用对的方式推荐给你"。

目标用户：18-35 岁，期望"像本地朋友推荐一样"的旅行体验，而非标准化的景点百科。

## User Flow

```
用户输入需求 ("我想去北京")
        |
        v
  +------------------+
  | 需求理解 (LLM)   |  模糊需求 -> 提取：目的地、偏好、预算、时间
  +--------+---------+
           |
           v
  +------------------+
   | 数据检索         |  从品味数据库查询匹配的景点/酒店/餐馆
  +--------+---------+
           |
           v
   +------------------+
   | 路线规划 (LLM)   |  根据数据生成时间线路线
   +--------+---------+
            |
            v
   +------------------+
   | 校验层           |  校验交通时间 + POI幻觉校验
   +--------+---------+
            |
            v
   +------------------+
   | 展示路线给用户   |  按时间轴展示各节点
  +--------+---------+
           |
           v
  用户反馈 ("肚子饿了" / "不想去天坛了")
           |
           v
  +------------------+
  | 实时调整 (LLM)   |  理解意图 -> 找新节点 -> 确认替换
  +--------+---------+
           |
           v
  更新路线展示
```

## Requirements

**核心路线规划**
- R1. 用户输入一段自然语言描述旅行需求（从模糊的"我想去北京"到清晰的"去北京吃烤鸭、去天安门、去天坛"），目的地为单一已覆盖城市（MVP 不支持多城市/跨城行程）。系统调用 LLM 提取结构化信息：目的地、天数、兴趣标签（与 taste_tags 受控词表对齐，词表定义见 Data Acquisition Pipeline 章节）、D1 游玩类型偏好（枚举：自然风光/历史人文/亲子娱乐/美食体验/文艺打卡/购物休闲）、D3 消费水平（1-5分）、D7 综合口碑（1-5分）、预算、回避项
- R2. 系统根据提取的结构化信息，采用**品味行程生成架构**（两阶段 LLM 调用 + 预筛选品味 POI 注入 + 校验层，详见对应章节）。MVP 只有品味行程模式一种流程，不做"标准模式"
- R3. 路线中的每个节点包含：名称、类型（景点/酒店/餐馆）、预估时长、位置、评分、推荐理由。品味模式下推荐理由以"本地朋友"口吻描述，包含氛围感受
- R4. 路线支持实时调整：用户输入修改意图（如"肚子饿了"、"不想去天坛了"），系统调用 LLM 理解意图，查找合适的新节点，向用户确认是否替换/插入/删除节点

**数据采集**
- R5. 系统从高德开放平台获取 POI 基础数据（名称/位置/评分/人均消费/类型），数据入库时直接映射 D1 游玩类型（从高德 POI 类型标签）、D3 消费水平（从高德人均消费字段）、D7 综合口碑（从高德评分字段）。评分>4.0 且非连锁的 POI 经 LLM 批量标注 taste_tags（受控词表选择，即 Tier B），其余仅存基础字段（即 Tier C）。存入数据库
- R6. MVP 阶段采用全量缓存策略（仅覆盖 1-2 个城市，不需要冷热区分）

**品味数据管理（分层自动化方案）**
- R7. 品味数据库存储每个 POI 的品味增强字段：taste_tags（品味标签）、recommend（是否推荐）、permanent_features（结构性特征）、tier（A/B/C 分层标识）、highlight_note（仅 Tier A：人工推荐语）
- R8. 品味数据分三层：
  - **Tier A（精选）**：10-15 个/城市，人工深度策展。团队亲自挑选的"真正值得一去"的地方，附个人推荐语。耗时 ~15-30 分钟/城市
  - **Tier B（自动）**：100-150 个/城市，高德 API + LLM 批量标注。脚本自动过滤评分>4.0 的非连锁品牌，LLM 生成 taste_tags（受控词表选择）。无 permanent_features。零人工耗时
  - **Tier C（基础）**：200+ 个/城市，高德原始数据。仅含 API 返回的基础字段（名称/位置/评分/消费/类型），无品味标注。用作覆盖面兜底
- R9. MVP 阶段先覆盖 1-2 个城市。数据获取流程为全自动化脚本（高德搜索 → 过滤 → LLM 标注）+ 人工精选 Tier A（~30 分钟/城市总投入）。**数据新鲜度**：每个 POI 记录 `last_verified` 时间戳，定期（月度）重新查询高德验证 POI 是否仍然存在/评分是否大幅下降。R15 的"不准"反馈也作为 POI 过期信号
- R10. SOUL 提示词按 tier 区分对待：Tier A 用人工推荐语重点描述，Tier B 用 LLM 标注信息标准描述，Tier C 只作补充

**前端交互**
- R11. 路线以时间轴形式可视化展示，每个节点可点击查看详情
- R12. 用户通过对话框输入需求和调整指令，系统以对话式交互响应
- R13. **前后端 API 契约**：核心 API 端点为 (1) POST /api/itinerary/generate（生成行程：请求体含用户自然语言输入，立即返回 itinerary_id，客户端随后订阅 SSE 接收进度和最终结果），(2) POST /api/itinerary/adjust（实时调整，请求体含行程 ID + 用户调整指令，返回变更预览），(3) POST /api/itinerary/adjust/confirm（确认调整，请求体含行程 ID + 变更预览索引，确认后生效），(4) POST /api/feedback（提交反馈，R15），(5) GET /api/itinerary/stream?itinerary_id={id}（SSE endpoint：连接后推送 Stage 1-4 进度事件，最终事件为 `event: complete` + 结构化行程 JSON；错误事件为 `event: error` + 错误码和用户友好消息）。对话状态为有状态会话设计——行程上下文持久化于 SQLite，每次请求携带行程 ID 加载完整上下文
- R14. 路线调整时，系统先展示变更预览（将替换/新增/删除的节点），用户确认后调用 POST /api/itinerary/adjust/confirm 生效
- R15. 行程展示页底部提供最小反馈入口："推荐准不准？"（准/一般/不准），点击后选项变为已选中状态并短暂显示"谢谢反馈！"，数据写入 SQLite，为品味数据优化提供基础信号

**页面信息架构（初步）**
- 页面布局：单页应用，垂直分三层——顶部固定标题栏（城市名 + 天数）、中部时间轴区域（可滚动，占主要空间）、底部固定对话框。**多日行程**：后端返回扁平节点列表（每节点含日期字段），前端按日期分组渲染，天与天之间用日期分隔线隔开
- 初始状态：空白页 + 对话框引导文案（如"告诉我你想去哪，我来帮你规划"）+ 示例行程链接
- 时间轴节点交互：点击节点展开详情面板（名称/类型/时长/位置/评分/推荐理由），非弹窗而是内联展开。展开时推开下方节点，面板内含关闭按钮，点击其他节点自动收起当前面板
- 调整预览：变更节点高亮显示（新增绿色、替换黄色、删除灰色），用户点击确认/取消按钮。**调整加载状态**：用户提交调整指令后、预览出现前，对话框显示加载提示，时间轴区域暂时锁定
- 进度状态：生成行程时时间轴区域显示 SSE 进度消息（Stage 1-4 对应文案见 Success Criteria）。**生成期间对话框禁用输入**，防止用户在生成过程中发送新请求；后端同步校验行程状态，拒绝生成进行中的行程重复请求
- 错误状态：网络错误显示顶部黄色提示条 + 重试按钮；校验失败节点显示灰色文字 + 提示图标
- 响应式：以 768px 为断点，移动端时间轴改为垂直布局，对话框保持底部固定
- 行程持久化：行程 ID 编码进 URL（/itinerary/{id}），支持浏览器刷新恢复。**恢复后交互状态与新建行程一致**——行程完整展示，对话框可继续输入调整指令，不回显历史消息但保留行程上下文

**前置验证（blocking prerequisite）**
- R16. 在正式开发前，必须完成 SOUL 提示词验证。验证分两阶段：
  - **Phase 0（验证阶段，1-2周）**：用最简工具（Jupyter notebook / Streamlit）+ 真实管线数据 + 直接 LLM API 调用（使用 **DeepSeek-V3** 模型）。不写后端代码、不建数据库。
    1. **高德数据质量审计**（前置，~30分钟）：(a) 对目标城市的 50 个品味类 POI（咖啡馆/书店/酒吧/小众餐厅等），查询高德 API 并统计字段完整度（rating/avg_cost/type 的填充率），分别统计品味类与常规类 POI 的填充率差异。(b) **品味类 POI 覆盖度审计**：从大众点评/小红书等来源整理目标城市 Top 20 品味类 POI，检查这些 POI 在高德中的收录率和字段丰富度。如果品味类 POI 收录率 <60% 或关键字段缺失率 >30%，需调整数据源策略或缩小品味类别范围
    2. **运行真实 Tier B 管线**：用目标城市的高德数据，跑完整的 Step 1（API 采集）+ Step 2（LLM 批量标注），产出真实的 Tier B taste_tags 数据
    3. **标签分布诊断**：统计 Tier B 的 taste_tags 频率分布。如果任何单一标签出现在 >60% 的 POI 中，或 <10 种标签组合覆盖了 >80% 的 POI，说明受控词表或标注逻辑需调整。**标签辨别力审计**：计算任意两标签组合的 POI 命中率，如果 Top-5 标签组合覆盖 >50% 的 Tier B POI，应扩展词表或引入子标签。同时人工抽查 20 个 Tier B POI 的 taste_tags 是否准确
    4. 手动创建 10 个 Tier A 品味 POI（含 permanent_features + highlight_note）
    5. 编写 SOUL 提示词和黄金示例
    6. **生成三组行程**用于盲测：
       - A 组：SOUL + Tier A（含 highlight_note）+ 真实 Tier B 管线数据
       - B 组：SOUL + Tier A（不含 highlight_note）+ 真实 Tier B 管线数据（对照实验，隔离数据质量变量）
       - C 组：竞品输出（携程AI/飞猪AI/ChatGPT，相同输入）
     7. **竞品盲测**：将 A/B/C 三组混合，让 **25 名**目标用户盲选"更像本地朋友推荐的"（三选一、n=25、60%通过率下达到 p≈0.05 统计显著性）。盲测评估的是行程规划质量与情绪价值的综合体验——不仅是有温度的语气，还包括路线合理性、节奏感、品味推荐的惊喜度
     8. **通过标准**：A 组在盲测中 ≥**60%** 被选为最佳，且无事实性编造。**注：60% 为初始阈值（可在 Phase 0 验证脚本中调整的常量），Phase 0 执行后根据实际数据分布调整**
    9. **失败标准**：A 组通过率 < 40% → 放弃当前架构，启用 Plan B
    10. **部分通过**：40%-59% → 调整 SOUL 提示词或受控词表重试一轮；**重试一轮后仍 < 60% 则启用 Plan B 子方案**
    - **判定权限**：Phase 0 结果由产品负责人 + 技术负责人联合判定。争议时产品负责人有最终裁决权。Plan B 启用需双方共同确认
    11. **关键诊断**：如果 A 组通过但 B 组显著低于 A 组，说明 highlight_note 在承载"本地朋友"效果，需评估 Tier A 规模化策略；如果 A/B 两组均通过，说明 SOUL 提示词本身是差异化来源
  - **Phase 1（系统开发）**：只有 Phase 0 通过后才进入。此时才开发后端架构、数据库、前端
  - **Plan B（如果 Phase 0 失败）**：(a) 缩窄到单一品类（如仅餐厅推荐），降低"品味"维度；(b) 改为人机混合模式（LLM 草拟 + 人工精修）

## Success Criteria

- 用户输入一句模糊需求（如"我想去北京"），系统返回一条可执行的路线。**响应时间**：暂不定具体SLA，Phase 0 验证时实测端到端延迟后确定合理目标。初步估算可能需 30-60 秒（含两次 LLM 调用 + 高德 API 校验），配合分阶段进度反馈管理用户等待预期。**流式输出为 post-MVP 优化项，MVP 先做整体返回。但必须实现分阶段进度反馈（**采用 SSE 机制推送**，Stage 1 完成时显示"正在了解你的需求..."，Stage 2 完成时显示"正在搜索品味好去处..."，Stage 3 完成时显示"正在规划你的专属行程..."，Stage 4 完成时显示"正在校验行程合理性..."）
- 品味行程模式下的节点描述能体现"本地朋友推荐"的口吻，区别于标准化的百科式介绍（R16 盲测通过率 ≥60%）
- MVP 上线后观察用户行为：是否有用户完成行程后返回查看或主动表示愿意推荐（定性观察，非定量硬指标）
- 校验层验证相邻节点间交通耗时，偏差>30% 时自动修正时间轴
- MVP 阶段至少覆盖 1-2 个热门城市的品味 POI 数据（Tier A 10-15 个 + Tier B 100-150 个 + Tier C 200+ 个/城市）
- R16 Phase 0 前置验证必须通过，否则需调整架构方案或启用 Plan B

## Scope Boundaries

- MVP 不做：支付/预订功能、社交分享、地图导航、多语言
- MVP 不做：App 端，仅 Web
- MVP 不做：实时价格比价
- MVP 不做：多城市/跨城行程规划，每次行程限于单一已覆盖城市
- 数据源 MVP 阶段早期开发可先 mock（静态 JSON 文件），正式运行前切换为真实 API（Data Acquisition Pipeline 脚本已定义完整流程）

## Key Decisions

- **Python + Vue 技术栈**：后端 Python（FastAPI），前端 Vue
- **缓存架构**：MVP 采用 SQLite 存储全部 POI 数据（数据量 < 1MB，可全量加载内存）。Parquet 序列化 + TTL + Per-key 并发保护为 post-MVP 扩展设计
- **后端分层架构**：MVP 采用 FastAPI 路由 + 服务函数两层结构。L1→L4 四层模式为 post-MVP 扩展设计
- **品味来自数据而非模型**：不做 fine-tuning，用 SOUL 提示词（人设+规则+黄金示例）+ 结构化品味数据注入控制输出质量
- **品味数据分层自动化**：高德 API 自动采集 + LLM 批量标注（Tier B/C）+ 人工精选 10-15 个 Tier A 亮点（~30 分钟/城市）。不依赖大规模人工运维
- **存结构性特征**：品味数据库存"藏在老社区里""老板养了只猫"这类长期稳定的特征，不存"今天有人排队"这种时态性观察
- **预筛选后注入上下文**：Tier A POI 全部注入（核心差异化），Tier B 按偏好筛选 10-15 个注入，总计约 20-30 个候选

### 合规性评估结论

| 平台 | 旅行攻略价值 | 获取难度 | 合规风险 | MVP 策略 |
|------|------------|---------|---------|---------|
| 大众点评 | 高（餐饮/景点 POI 结构化） | 极高（字体反爬+法律维权积极） | 🔴 高 | 用高德/百度 POI 替代 |
| 小红书 | 极高（UGC 攻略内容质量最高） | 高（签名加密+设备指纹） | 🟠 中高 | 人工整理 + 官方合作探索 |

| **景点介绍** | 高德 POI 搜索 | Wikipedia API + Wikivoyage | 历史/文化介绍文案 ✅；注意：Wikipedia 对小众 POI（独立咖啡馆/书店等）覆盖度低，Tier B/C 的介绍主要靠 LLM 基于 POI 数据生成 |
| **天气** | 高德天气 API | - | 实时天气/预报 ✅ |

**核心结论：** 高德开放平台为主数据源，百度地图补充营业时间/POI图片，Wikipedia 提供景点文化介绍。门票价格为最大数据空白，需自行维护或爬取景区官网。

### 数据空白与应对

| 缺失字段 | 影响 | 应对方案 |
|---------|------|---------|
| 门票价格 | 路线预算计算不准确 | 人工维护热门景区门票表 + 后期爬取景区官网 |
| 用户评价文本 | 缺少真实用户反馈感 | 用 LLM 基于 POI 数据生成简介 |
| 实时人流量 | 无法推荐"避开人挤人" | 用评分+评价数估算热度，后期接入高德实时路况推断 |

## POI 八维度评分体系设计 (2026-04-15)

> **⚠️ 以下为 post-MVP 扩展设计。MVP 仅使用 D1/D3/D7/taste_tags 四个维度。实现者可跳过本章节，直接进入 Data Acquisition Pipeline。**

设计原则：每个维度必须（1）能从高德 POI 数据 + LLM 推断中获取，（2）直接对应用户常见的表达方式，（3）对路线规划有实际排序价值。

### 维度总览

| # | 维度 | 分值范围 | 对应用户表达 | 数据来源 |
|---|------|---------|------------|---------|
| D1 | 游玩类型 | 枚举标签 | "看古迹"、"吃烤鸭"、"带孩子玩" | LLM 根据高德 POI 类型标签 + 名称分类 |
| D2 | 适合人群 | 枚举标签 | "带爸妈"、"情侣出行"、"一个人" | LLM 根据景点特征推断 |
| D3 | 消费水平 | 1-5 | "预算不多"、"不差钱"、"人均多少" | 高德人均消费 + 价格等级字段 |
| D4 | 游玩时长 | 1-5 | "就路过看看"、"不想赶"、"慢慢逛" | LLM 根据景点类型+面积推断 |
| D5 | 体力消耗 | 1-5 | "累了"、"不想走太多路"、"轻松点的" | LLM 根据景点类型+面积推断 |
| D6 | 热度 | 1-5 | "热门景点"、"小众推荐"、"不想人挤人" | 高德评分 + 评价数量 + 文旅部等级 |
| D7 | 综合口碑 | 1-5 | "评价好的"、"口碑怎么样"、"踩不踩雷" | 高德评分 + 评价数量 |
| D8 | 时段适配 | 枚举标签 | "晚上有什么好玩的"、"下雨天怎么办" | LLM 根据景点特征推断（室内/室外/夜景/全天） |

### 各维度详细定义

**D1 — 游玩类型**（枚举标签，可多选）

| 子类型 | 说明 | 示例 |
|--------|------|------|
| 自然风光 | 山水/公园/湖泊/海滩 | 西湖、张家界 |
| 历史人文 | 古迹/博物馆/寺庙/纪念馆 | 故宫、兵马俑 |
| 亲子娱乐 | 游乐园/动物园/水族馆/科技馆 | 迪士尼、长隆 |
| 美食体验 | 特色餐饮/小吃街/老字号 | 全聚德、簋街 |
| 文艺打卡 | 展览/创意园/网红店/书店 | 798、方所 |
| 购物休闲 | 商场/步行街/奥特莱斯 | 南锣鼓巷、太古里 |

**D2 — 适合人群**（枚举标签，可多选）

| 子类型 | 说明 |
|--------|------|
| 亲子 | 儿童友好、有亲子设施 |
| 情侣 | 浪漫氛围、适合二人世界 |
| 朋友 | 适合多人互动、热闹 |
| 独行 | 安全、不尴尬、自由度高 |
| 老年 | 步行少、有休息区、无高强度活动 |
| 团建 | 承载量大、有集体活动 |

**D3 — 消费水平**（1-5 分）

| 分值 | 含义 | 餐饮参考 | 景点参考 |
|------|------|---------|---------|
| 1 | 免费/极低 | 人均 ≤30 | 免费景点 |
| 2 | 低消费 | 人均 30-60 | 门票 ≤30 |
| 3 | 中等 | 人均 60-120 | 门票 30-80 |
| 4 | 偏高 | 人均 120-250 | 门票 80-200 |
| 5 | 高消费 | 人均 >250 | 门票 >200 |

**D4 — 游玩时长**（1-5 分）

| 分值 | 含义 | 时长范围 |
|------|------|---------|
| 1 | 快速打卡 | ≤30 分钟 |
| 2 | 短暂游览 | 30分钟-1小时 |
| 3 | 半日游 | 1-3 小时 |
| 4 | 大半日 | 3-5 小时 |
| 5 | 全天深度 | 5 小时以上 |

**D5 — 体力消耗**（1-5 分）

| 分值 | 含义 | 特征 |
|------|------|------|
| 1 | 几乎不走路 | 坐着体验（剧场、餐饮） |
| 2 | 轻松休闲 | 少量步行，有代步工具 |
| 3 | 适度步行 | 正常游览步行量 |
| 4 | 较大运动量 | 爬山、长距离步行 |
| 5 | 高体能要求 | 登山、徒步、户外探险 |

**D6 — 热度**（1-5 分）

| 分值 | 含义 | 推断依据 |
|------|------|---------|
| 1 | 冷门 | 高德评价数少，非 A 级景区 |
| 2 | 小众 | 少量评价，有一定知晓度 |
| 3 | 普通 | 中等评价数，3A/4A 景区 |
| 4 | 热门 | 大量评价，4A/5A 景区 |
| 5 | 顶流 | 超高评价数，5A 景区，城市地标 |

**D7 — 综合口碑**（1-5 分）

| 分值 | 含义 | 推断依据 |
|------|------|---------|
| 1 | 口碑差 | 高德评分 ≤3.0 或大量差评 |
| 2 | 口碑一般 | 高德评分 3.0-3.8 |
| 3 | 口碑良好 | 高德评分 3.8-4.3 |
| 4 | 口碑优秀 | 高德评分 4.3-4.7，评价数量多 |
| 5 | 口碑极佳 | 高德评分 ≥4.7，大量正面评价 |

> **与 D6 热度的区别：** 热度衡量的是"多火"（流量维度），口碑衡量的是"多好"（质量维度）。热门景点可能口碑一般（如某些商业景点），小众景点可能口碑极佳（如隐藏宝藏店）。

**D8 — 时段适配**（枚举标签，可多选）

| 子类型 | 说明 | 示例 |
|--------|------|------|
| 上午 | 适合上午游览 | 多数景点 |
| 下午 | 适合下午游览 | 博物馆、室内展 |
| 夜景 | 适合晚上游览 | 外滩、洪崖洞 |
| 全天 | 任何时段都可以 | 商业街、公园 |
| 室内 | 不受天气影响 | 博物馆、商场 |
| 室外 | 受天气影响 | 公园、古迹 |

### 维度与用户输入的匹配逻辑

> **注意：以下示例基于完整的 D1-D8 体系。MVP 仅使用 D1/D3/D7/taste_tags，匹配逻辑需相应简化。**

LLM 解析用户自然语言后，输出一组维度偏好：

```
用户输入: "带爸妈去北京，不想太累，看看历史古迹，预算适中，评价好的"
        |
        v
LLM 提取:
  D1 游玩类型: [历史人文]
  D2 适合人群: [老年]
  D3 消费水平: 3 (中等)
  D5 体力消耗: ≤2 (不想太累)
  D7 综合口碑: ≥4 (评价好的)
  D8 时段适配: [室内] (老年人体力有限，优先室内)
        |
        v
系统过滤: 老年+历史人文+低体力+高口碑 → 推荐: 故宫(口碑5)、国博(口碑5)、天坛(口碑4)
系统排除: 长城(体力5)、某些商业景点(口碑2)
```

### 维度匹配的边界情况处理

> **注意：以下边界处理逻辑基于完整的 D1-D8 体系。MVP 阶段仅 D1/D3/D7/taste_tags 可用于过滤，边界处理需相应简化。**

**核心策略：逐步放宽，不是报错返回空。**

当用户约束组合导致候选结果不足时，按优先级逐步放宽维度，而非直接返回"无结果"。维度分为两类：

- **硬约束（不可放宽）**：D1 游玩类型、D2 适合人群 —— 这些是用户明确表达的意图，放宽等于无视用户需求
- **软约束（可逐步放宽）**：D3 消费、D4 时长、D5 体力、D6 热度、D7 口碑、D8 时段 —— 放宽后仍能给出有意义的结果

#### 边界场景与处理策略

| # | 场景 | 示例 | 处理策略 |
|---|------|------|---------|
| 1 | **过度约束：零结果** | "免费的、口碑5分、不累的、小众的、历史古迹" → 候选为空 | 按维度优先级逐步放宽：先放宽 D6 热度 → 再放宽 D8 时段 → 再放宽 D5 体力 → 再放宽 D3 消费 → 再放宽 D7 口碑 → 最后放宽 D4 时长。每次放宽后重新查询，直到结果 ≥3 个 |
| 2 | **矛盾约束** | "免费 + 口碑极佳" 或 "全天深度 + 不累" | LLM 在提取阶段识别矛盾，向用户主动确认："免费景点口碑一般较好但评价数量少，是否接受口碑 3 分以上的？" |
| 3 | **过于模糊** | "北京有什么好玩的" 无任何偏好 | 不过滤，按 D7 口碑 + D6 热度综合排序，返回城市 Top 20 热门 POI 供 LLM 挑选 |
| 4 | **过于具体（精确匹配）** | "去全聚德吃烤鸭" 明确指定了某个 POI | 直接命中该 POI，不走维度过滤流程，路线规划围绕它展开 |
| 5 | **约束组合只剩单一类型** | "免费 + 不累 + 室内" → 只剩博物馆类 | 正常返回结果，但 LLM 在生成路线时主动提醒："根据您的偏好，以下以博物馆类为主，如果想换换口味可以告诉我" |
| 6 | **路线时间塞不下** | 用户只留了 2 小时，但筛选出的景点都要 3 小时 | 放宽 D4 时长约束，引入时长更短的 POI（D4=1 或 2），若仍不够则拆分为多段建议 |
| 7 | **实时调整导致路线断裂** | "不去天坛了" 删掉中间节点，前后节点距离过远 | LLM 重新规划该段路线，在原位置插入合适的填充节点（优先从附近高 D7 口碑的 POI 中选择） |
| 8 | **用户临时改变偏好方向** | 原本"看古迹"，中途说"想吃东西" | 不丢弃原偏好，将新偏好叠加：在当前路线附近搜索 D1=[美食体验] 的节点，插入或替换当前时段 |

#### 放宽优先级（从最不重要到最重要）

```
D6 热度 → D8 时段 → D5 体力 → D3 消费 → D7 口碑 → D4 时长
   ↑                                                            ↑
 最先放宽                                                    最后放宽
```

**理由：**
- 热度最先放宽——"热门"和"小众"对用户体验影响最小
- 时段次之——下午去本该上午去的景点，体验差异不大
- 口碑和时长最后放宽——这两个直接影响"踩不踩雷"和"时间够不够"，是用户最在意的

## Data Acquisition Pipeline (2026-04-15)

### 数据获取全流程（自动化 + 最小人工）

```
Step 1: 高德 API 采集（Python 脚本，~50行，一次编写）
├── 注册高德开放平台 (lbs.amap.com)，创建应用，获取 API Key（免费，5分钟）
├── 脚本按城市+关键词调用 POI 搜索 API：
│   - 关键词列表：["景点", "咖啡馆", "餐厅", "书店", "酒吧", "酒店", "博物馆", ...]
│   - 每个关键词返回最多 200 条结果
├── 自动分类：评分 > 4.0 且非连锁的标记为 Tier B 候选，其余标记为 Tier C，全部存入数据库（判定规则：高德 POI 的 brand_id 字段非空则视为连锁；补充黑名单：星巴克/肯德基/麦当劳/瑞幸/海底捞等）
├── 存入 SQLite 数据库（全量 POI 表）
└── 运行耗时：5-10 分钟/城市 → 得到 300-500 个 POI（含 Tier B + Tier C）

Step 2: LLM 批量标注（Python 脚本，~30行，一次编写）
├── 对 Step 1 过滤后的 POI（评分>4.0 且非连锁，约 100-150 个）
├── 批量调用 LLM："这个 POI 叫{name}，类型{type}，评分{rating}，人均{cost}元，位于{city}
│   请从以下词表中选择 2-3 个匹配的品味标签：[受控词表，见下方]
│   不需要生成 permanent_features"
├── LLM 返回 taste_tags（从受控词表选择，确保可精确匹配）
├── 标记 tier='B'（注意：Tier B 无 permanent_features，仅有 taste_tags）
└── 运行耗时：~30分钟/城市 | 成本：~¥0.4/城市（DeepSeek）

Step 3: 人工精选 Tier A（浏览器/表格界面）
├── 打开 Step 2 标注好的 POI 列表
├── 浏览并挑选 10-15 个你真的觉得好的地方
├── 标记 highlight=true, tier='A'
├── 填写 permanent_features（长期稳定的结构性特征，如"藏在老社区里""二楼有湖景"）
├── 写一句个人推荐语（highlight_note），如"老板是退休摄影师，店里有只猫"
└── 耗时：15-30 分钟/城市

总计：~30 分钟人工/城市（从采集到 Tier A 精选）
```

### 品味 POI 数据结构（分层）

```json
{
  "name": "XX咖啡馆",
  "poi_id": "B0xxx",
  "location": {"lat": 30.25, "lng": 120.15},
  "rating": 4.5,
  "avg_cost": 45,
  "type": "餐饮",
  
  "tier": "A",
  "taste_tags": ["独立", "安静", "适合发呆"],
  "recommend": true,
  "permanent_features": ["藏在老社区里", "二楼有湖景"],
  "highlight_note": "老板是退休摄影师，店里有只橘猫，下午三点阳光最好",
  "last_verified": "2026-04-15T00:00:00Z"
}
```

| 字段 | Tier A | Tier B | Tier C |
|------|--------|--------|--------|
| name/location/rating/avg_cost/type | ✅ 高德API | ✅ 高德API | ✅ 高德API |
| taste_tags | ✅ LLM初标+人工审核 | ✅ LLM从词表选择 | ❌ |
| recommend | ✅ true | ✅ true | ❌ |
| permanent_features | ✅ 人工编写 | ❌（Tier B 无此字段） | ❌ |
| highlight_note | ✅ 人工推荐语 | ❌ | ❌ |
| last_verified | ✅ 入库时间戳 | ✅ 入库时间戳 | ✅ 入库时间戳 |
| tier | "A" | "B" | "C" |

### taste_tags 受控词表（LLM 从此表选择，不发明新标签）

| 类别 | 标签 |
|------|------|
| 氛围 | 安静、热闹、文艺、复古、现代、小资、市井、隐秘 |
| 适合 | 适合发呆、适合拍照、适合约会、适合独处、适合带娃、适合聚会 |
| 特色 | 独立、本地特色、老字号、网红、新锐、手工、现场制作 |
| 场景 | 室内、户外、有露台、有花园、临水、山上、地下 |
| 时段 | 适合早晨、适合下午、适合夜晚、全天 |
| 偏好 | 小众、经典、性价比高、高端、随意、仪式感 |

不追求"全"，只追求"准"。**MVP 词表以上表为准，Phase 0 步骤3 标签分布诊断后视结果决定是否扩展。** 入选 Tier A 的 POI 需满足至少一条：
- 你自己去过且真心觉得好
- 身边朋友强烈推荐过
- 在小红书/大众点评有高质量真实推荐（非广告）
- 有独特体验（"唯一能XX的地方""老板会XX"）

## 品味行程生成架构 (2026-04-15)

### 架构总览

```
用户输入 → [Stage 1: 意图提取 LLM] → 结构化偏好
                                         ↓
                                    [Stage 2: 数据预筛选] → 品味数据库 + 高德POI → 20-30个候选
                                                                           ↓
                                                              [Stage 3: 行程生成 LLM] → 结构化行程JSON
                                                                                         ↓
                                                                              [Stage 4: 校验层] → 最终行程
```

### Stage 1: 意图提取

单次 LLM 调用，约 500 token。输入用户自然语言，输出结构化偏好：目的地（单一城市）、天数、兴趣标签（从 taste_tags 受控词表选择）、D1 游玩类型（从枚举选择）、D3 消费水平（1-5分）、D7 综合口碑（1-5分）、预算、回避项。**如果用户指定天数超过 3 天，提示"MVP 阶段最多支持 3 天行程"并建议缩短。**如果用户输入不包含目的地信息（如"周末想出去玩"），返回追问消息请用户指定目的地，不自动推测。如果用户指定多城市，提示"MVP 阶段仅支持单一城市行程"。

LLM 输出格式：Stage 1 和 Stage 3 的 LLM 输出需定义 JSON schema（可引用路线节点结构）。Stage 1 解析失败时重试 1 次（重试时将上次错误信息作为 few-shot 反馈传入），仍失败则返回错误提示。

### Stage 2: 数据预筛选（纯代码，不调用 LLM）

**MVP 简化方案**：
1. **Tier A POI（10-15 个）全部注入**，不做预筛选——数据量小，token 开销可控（约 2,000 token），且是核心差异化来源
  2. **回避项过滤**：排除 taste_tags 与用户回避项交叉的 POI，排除 D1 类型与用户回避类型匹配的 POI（如用户说"不想逛街"→排除 D1=购物休闲）。**Tier A 回避降级逻辑**：Tier A 不直接排除，但如果 Tier A POI 的 taste_tags 与用户回避项完全匹配（如用户说"不想去安静的地方"且该 Tier A 标签含"安静"），该 Tier A POI 降级为 Tier B 待遇——注入时不引用 permanent_features 和 highlight_note，仅以基础字段 + taste_tags 揢述。用户明确排除的特定 POI 仍然直接排除
  3. 从 Tier B 中按 taste_tags 匹配用户兴趣（受控词表精确匹配）
4. 过滤预算范围外的 Tier B POI
5. 按与最近 Tier A POI 的距离排序 Tier B 候选，去掉距离过远的孤立点（**默认阈值 10km（硬编码常量，后续按需参数化）。如果用户偏好含远郊意图如"长城"，自动放宽距离过滤**）
6. Tier B 保留 Top 10-15 个候选
7. 最终注入 LLM 的候选集 = Tier A 全部（10-15 个）+ Tier B 筛选后（10-15 个）≈ 20-30 个

**兜底逻辑**：如果 Tier B 筛选后候选数 < 5，逐步回退距离限制 → 预算过滤 → taste_tags 匹配，直到候选 ≥ 5。如果完全回退后仍为 0，仅用 Tier A POI 生成行程。

**候选池覆盖度检查**：筛选完成后，检查候选池是否覆盖用户预期需要的主要类型（景点/餐饮/休闲等）。如果某类型（如餐饮）在候选池中 < 2 个且用户未明确排除该类型，从 Tier C 中补充该类型的高评分 POI（按 rating 排序取 Top 2-3 个，标注为 Tier C 基础数据）。

### Stage 3: 行程生成

单次 LLM 调用，输入约 8,300-9,300 token（SOUL 2K + POIs 6-7K + 偏好 200 + 约束 100），输出约 2,500-4,000 token（多天行程含详细描述），总计约 11,000-13,000 token。**计划使用 ≥100K 上下文窗口的模型**，窗口利用率到达 85% 时自动压缩摘要（保留 POI 核心字段，裁剪冗余描述）。**MVP 天数上限 3 天**（Stage 1 应拒绝或提示超长行程）。**Stage 3 为最昂贵调用（~12K token），解析失败时重试 1 次并简化 JSON 结构要求，仍失败则返回错误提示。**
- SOUL 部分（人设定义 + 推荐规则 + 黄金示例，约 2,000 token）
- 预筛选后的 20-30 个品味 POI 数据（约 6,000-7,000 token）
- 用户偏好（Stage 1 输出，约 200 token）
- 路线约束（约 100 token）

SOUL 规则核心约束：
- 只推荐列表中给出的 POI，不编造（**Stage 4 程序化校验**：逐个验证推荐 POI 的 poi_id 存在于 Stage 2 候选集中，幻觉 POI 替换为最近的 taste_tags 匹配项）
- 描述氛围和感受，不编造时态性事实
- Tier A POI 优先引用 permanent_features 和 highlight_note；Tier B POI 仅基于 taste_tags 和基础数据描述（**注入时 Tier B 省略 permanent_features 和 highlight_note 字段**）
- 每天不超过 4 个节点，留出发呆/闲逛时间

### Stage 4: 校验层（纯代码，调用高德路线 API）

逐**相邻**节点对验证节点间距离和时间（O(N)复杂度），与 LLM 输出对比。偏差>30% 时自动修正时间轴。**每日节点数校验**：如果任一天 >4 个节点，移除该天评分最低的 Tier B/C 节点（保留 Tier A）。**POI 幻觉校验**：逐个验证推荐 POI 的 poi_id 存在于候选集中，幻觉 POI 先在候选集中按地理距离找最近的候选（距离约束），再在该候选的 taste_tags 中匹配用户兴趣标签进行替换。如果候选集中无任何可替换候选（距离超出合理范围或 taste_tags 无匹配），前端弹窗提示"AI 推荐了一个数据中不存在的地点，已自动移除"，并从行程中删除该节点。**Tier B/C 描述校验**：SOUL 提示词增加硬约束——"对于 Tier B/C POI，只能基于给出的 taste_tags 和基础字段描述，不得推测未提供的特征（如装修风格、店主故事、菜品推荐等）"。**校验失败处理**：高德路线API超时时，跳过校验并在节点标记 transport_verified: false + transport_note: "交通时间未经校验，仅供参考"，前端渲染为灰色文字+提示图标；POI幻觉校验失败时按地理距离+taste_tags匹配规则替换或删除节点并弹窗提示"AI 推荐了一个数据中不存在的地点，已自动移除"

### 品味 POI 数据结构（注入 LLM 的子集）

注入 LLM 时不含 tier（系统内部字段）。Tier A 注入时包含 highlight_note，Tier B 不含 permanent_features 和 highlight_note：

```json
{
  "name": "XX咖啡馆",
  "poi_id": "B0xxx",
  "location": {"lat": 30.25, "lng": 120.15},
  "rating": 4.5,

```

Tier B 注入时省略 permanent_features 和 highlight_note 字段：```json

## External API Error Handling

- **高德 API 失败**：校验层（Stage 4）如果高德路线 API 超时/限流/错误，跳过校验直接返回 LLM 生成的时间估计，并在行程 JSON 中对该节点标记 `transport_verified: false` 和 `transport_note: "交通时间未经校验，仅供参考"`，前端据此渲染不同 UI 状态（如灰色文字+提示图标）。数据采集失败则重试 2 次，间隔 1 秒，仍失败则跳过该 POI
- **LLM API 不可用**：返回用户友好的错误页面"服务暂时不可用，请稍后再试"，不展示技术细节。不做离线降级（MVP 阶段接受此风险）
- **品味数据未覆盖的城市**：MVP 仅接受已覆盖城市的输入，不支持的城市直接提示"暂未覆盖，目前已支持：[城市列表]"，引导用户选择已覆盖城市。**不做降级 LLM-only 模式**——产品定位为品味行程生成器，通用 AI 推荐与定位矛盾。**覆盖策略**：MVP 以 1-2 个城市完成品味推荐核心假设验证（R16 Phase 0 + 定向测试用户），验证通过后再规模化拓展城市覆盖。MVP 阶段不面向大众开放，以定向测试为主

## Real-Time Adjustment POI Strategy

实时调整时（R4），如果用户的新需求超出预筛选的 20-30 个候选范围（如"肚子饿了"但候选中无餐饮），系统从品味数据库重新查询匹配新意图的 POI。重新查询规则：先由 LLM 将用户意图映射为 D1 类型（如"肚子饿了"→ D1=美食体验），**按 D1 类型过滤候选 POI**，再按新意图的 taste_tags 精细筛选。**位置策略**：MVP 不推断用户位置。POST /api/itinerary/adjust 请求体可选 `location` 字段（lat/lng），前端在调整时展示简易位置选择器（从行程已有节点列表中选择，或通过对话框自然语言输入位置由后端调用高德地理编码解析）。如果用户不输入位置，默认以行程中下一个未完成节点的位置为搜索中心，半径 3km 范围内，返回 Top 5 候选。如果 3km 内无匹配，逐步扩大至 5km → 10km，并在推荐时标注距离。超过 10km 仍无结果时告知用户附近暂无推荐。SOUL 规则"只推荐列表中 POI"针对每次 LLM 调用独立生效——实时调整时的"列表"是重新查询后的结果。

## 关于八维度评分体系

本文档中的八维度评分体系（D1-D8）是**目标设计**，非 MVP 必须全部实现。R5 已注明"MVP 简化为类型标签+评分+消费水平"。MVP 阶段实际使用的维度：
- **D1 游玩类型**：从高德 POI 类型标签直接映射（枚举：自然风光/历史人文/亲子娱乐/美食体验/文艺打卡/购物休闲）
- **D3 消费水平**：从高德人均消费字段直接获取（1-5 分，参考"各维度详细定义"中 D3 分值表）
- **D7 综合口碑**：从高德评分直接获取（1-5 分，参考"各维度详细定义"中 D7 分值表）
- **taste_tags**：Tier A 由 LLM 初标后人工审核（继承 Tier B 管线产出，人工挑选时确认标签准确），Tier B 由 LLM 从受控词表选择（MVP 以 Tier B 为主）

其余维度（D2/D4/D5/D6/D8）在 MVP 后期根据需要逐步引入。

## Competitive Moat

品味数据库本身可被复制（300-400 行数据，1 周可重建），但竞争壁垒来自：
1. **SOUL 提示词 + 黄金示例的组合**：需要大量调试才能产出有温度的行程，这是隐性知识
2. **品味数据与 SOUL 提示词的适配**：换一批数据需要重新调整提示词，数据和提示词是耦合的
3. **先发用户反馈循环**：用户使用后产生的反馈（"推荐很准/不准"）可反哺品味数据优化。**数据版本管理**：品味数据标记版本号（如 data_v1_beijing），SOUL 提示词记录适配的数据版本。数据更新时用回归测试集验证输出质量是否退化

MVP 阶段壁垒确实薄弱，但验证方向比保护壁垒更重要。

## Dependencies / Assumptions

- 假设：大众点评、小红书、B站等平台直接爬取的合规风险过高，MVP 阶段以地图 POI + 人工整理为主
- 依赖：至少一个大模型 API 的可用性（OpenAI / DeepSeek / Claude）
- 依赖：高德地图 API Key 的获取（免费额度通常足够 MVP）
- 假设：SOUL 提示词行为在 LLM 模型版本更新时保持稳定。缓解：锁定模型版本（如 deepseek-v3-2026-04），Phase 0 的 5 条示例行程作为回归测试集，模型更新后自动验证输出质量。**风险**：LLM 厂商可能退役特定版本端点，锁定版本不可用时需在新模型上重新调优 SOUL 提示词——回归测试集可检测退化但不能保证新模型上能调到同等质量。缓解措施：优先选择有版本稳定性承诺的厂商，回归测试不通过时保留回退到最近可用版本的能力
- 假设：用户使用中文交互
